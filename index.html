Y-SAFE (청년야호) — 청년 경제위험 진단 · 정책 매칭

🏆 AI 특별상 · 발제사별 3등상
BUSAN DIVE 2026 해커톤 · 팀 깐부 (2인) · 담당: 합성데이터 분석, 서비스 기획, UX 디자인

"누가 위험하고, 누구에게 먼저 예산을 써야 하는가" — 연체 발생 전 선행 신호로 청년 경제위기를 조기 포착하고, 예산 제약 하의 최적 배정까지 답하는 시민 앱(청년야호) + 행정 대시보드(Y-SAFE).

ML · 데이터 기여

  • KCB 원본 42개 컬럼 → 파생변수 15종 → 도메인지수 5종(주거비압박·부채상환위험·소득변동성·소비압박·신용취약)으로 변환하는 피처 엔지니어링 설계
  • GMM 소프트 클러스터링(BIC 기준 K 자동 선택)으로 위기 유형 진단, LightGBM + SHAP으로 위험 확률 산출 — held-out PR-AUC 0.9032 실측
  • 리허설 중 비정상 고성능을 데이터 누수(Leakage)로 의심 → 신용취약지수를 통한 연체심각도 우회 유입 경로를 규명하고 예측 피처에서 프로그램적(assert) 차단
  • LP/MIP 수리최적화로 예산 제약 하 정책 배정, 쉐도우 프라이스로 정책별 한계효율 순위 산출 · 예산 스윕 민감도 분석
  • Global Moran's I 검정(999회 순열)으로 위험의 공간 무상관성을 증명해 "지역 타겟팅이 아닌 개인 단위 진단" 근거 도출, Equalized-Odds 공정성 보정 실적용
  • 온통청년 Open API 실연동, 테스트 445건 통과 — Kotlin Compose 앱 + React 대시보드 + FastAPI, 실동작 제품 3종 완성

문제 정의

부산 청년 1인가구는 약 20만 가구, 청년 평균 부채는 2,465만 원. 주거비 부담 → 대출 의존 → 상환 부담 → 연체로 이어지는 악순환에서 연체가 발생한 뒤에는 이미 늦습니다. 기존 플랫폼에 AI 정책 추천은 있었지만, 위기 선제 포착과 예산 최적 배정 기능은 부재했습니다.

접근 — 챗봇이 아니라 선제 계산

문의자에게만 반응하는 Pull형 챗봇 대신 인구 전체를 선제 계산하는 Push형 시스템을 설계했습니다. "나에게 맞는 정책이 있나요?"가 아니라 "누가 위험하고, 누구에게 먼저인가"에 답하고, 매칭 실패 케이스는 버리지 않고 미충족 수요 데이터로 축적해 신규 정책 제안 근거로 환류합니다.

피처 엔지니어링 · 모델

원본 42개 컬럼을 파생변수 15종으로 가공해 주거비압박·부채상환위험·소득변동성·소비압박·신용취약의 5종 도메인지수로 압축했습니다. GMM 소프트 클러스터링(BIC 기준 K 자동 선택)으로 위기 유형을 진단하고 LightGBM + SHAP으로 위험 확률과 요인 설명을 산출합니다. 신용이력 없는 Thin Filer는 별도 보정 서브모델로 처리하고, 결측치 임의대체 금지·safe_divide 등 데이터 원칙을 코드로 강제했습니다.

트러블슈팅 — 성능을 의심하는 장치

리허설 중 위험모델 성능이 비정상적으로 높게 나오자 데이터 누수를 의심했습니다. 연체 변수를 직접 넣지 않았는데도 신용취약지수를 통해 연체심각도가 우회 유입되는 경로를 규명했고, 진단(클러스터링)에는 허용하되 예측 피처에서는 assert로 차단하는 완전 분리 설계를 적용했습니다.

공간분석 · 검증

Global Moran's I(999회 순열검정)로 위험이 공간적으로 군집하지 않음을 확인해 "지역 타겟팅이 아닌 개인 단위 진단"의 근거를 세웠고, 절대수 대신 1천명당 정규화 시 위험 순위가 역전됨을 보였습니다. 국토부 전월세 실거래 213,872건으로 역전세 위험 파생변수를 구축해 사상구의 전세가 -16.6% 하락 위험을 포착했으며, 성별·연령대 그룹에 Equalized-Odds 임계값 보정을 실제 적용했습니다.

한계와 로드맵

위험점수는 단일 시점 프록시 점수임을 전제로 명시했고, 패널데이터 확보 시 Cox 생존분석으로 교체되도록 코드를 미리 구현해 두었습니다.

Tikkle (티끌) — 식비 절약 · 냉장고 관리 서비스

팀 프로젝트 · 4인
2026.03 – 2026.04 (4주) · 담당: 데이터 파이프라인, OCR 정제, ML 예측 모델, 레시피 추천 알고리즘

OCR 영수증 인식으로 식재료를 자동 등록하고, ML 유통기한 예측과 레시피 추천으로 식재료 낭비와 식비를 줄여주는 통합 관리 서비스.

ML · 데이터 기여

  • Random Forest 회귀 유통기한 예측 모델 구축 — 식품분류 46종·보관조건 7종·품목 229종을 LabelEncoder로 인코딩, 신선식품 0.7~기타 0.9의 카테고리별 안전 가중치로 보수적 D-Day 산출
  • 미학습 품목 유입 시 RapidFuzz 유사도 80 이상이면 최근접 품목 예측치를 차용하는 폴백 로직으로 예외 방어
  • 유통기한 임박 가중치 W(x) = 10/√(x+1)을 결합한 코사인 유사도 CBF 설계 + 실서비스에는 주재료 3.0 / 부재료 1.5 / 양념 0.5의 역할별 가중치 매칭 스코어 추천 라우터 적용
  • EDA로 추천 실행 가능성 검증 — 조리시간 60분 이하 98.4%(1,238개), 난이도 1~2가 97.7%임을 확인해 일상 조리 적합성 입증
  • Google Vision OCR 후처리 — "국산 우리 콩두부 100g" → "두부"식 대표 키워드 정규화, 영수증 총액의 예산 실시간 차감·게이지 차트 시각화
  • OpenAI API + JSON Schema 응답 형식, max_output_tokens=700 토큰 최적화 프롬프트로 제철요리 원터치 추천 구현

데이터 파이프라인

공공 API 원천 데이터에서 불필요한 메타데이터 컬럼을 제거하고, '60분 이내'·'2시간 이상' 같은 비정형 조리시간을 분 단위 정수로 정규화했습니다. 문장형 재료 설명을 주재료·부재료·양념 3속성으로 분리해 매칭 엔진 기준선을 만들고, recipe_id 인덱스를 설계해 RDBMS 적재 가능한 마스터 데이터셋으로 통합했습니다.

예측 모델 · 예외 방어

RandomForestRegressor(n_estimators=100)에 식품분류 46종·보관조건 7종·품목 229종을 LabelEncoder로 인코딩해 입력합니다. 미학습 품목은 RapidFuzz 유사도 80 이상 시 최근접 품목 예측치를 차용하고, 분류 체계 밖 값은 '기타가공품'으로 매핑하는 아웃라이어 가드를 뒀습니다. 예측치를 과신하지 않도록 신선식품·육류 0.7 ~ 기타 0.9의 안전 가중치로 보수적인 D-Day를 저장합니다.

추천 알고리즘 — 이론과 실서비스의 격차

이론 모델은 코사인 유사도에 유통기한 임박 가중치 W(x)=10/√(x+1)를 결합해 임박 재료가 상단에 오도록 설계했습니다. 실서비스 API에는 주재료 3.0 / 부재료 1.5 / 양념 0.5 역할별 배점 라우터가 연결돼 있는데, 이 버전이 임박도를 반영하지 못하는 아키텍처 격차를 스스로 문서화하고 D-Day 필터 결합 고도화 방향을 제시했습니다.

Mechuri — 위치 기반 점심 메뉴 · 식당 추천 앱

팀 프로젝트
2026.02 – 2026.03 (4주) · 담당: 데이터 수집·정제 파이프라인, 규칙 기반 개인화 추천

"오늘 뭐 먹지?"를 해결하는 추천 앱. 원천 데이터의 결측·노이즈를 관찰하며 정제 규칙을 반복 개선해, 추천 서비스에 바로 쓸 수 있는 데이터셋을 직접 구축.

데이터 · 추천 성과

  • 주소·좌표 결측을 통계값 대체가 아닌 Kakao Local API 재조회로 보강 — 위치 데이터 특성에 맞는 결측 처리 전략 적용
  • 음식점명·브랜드명 키워드 기반 규칙 재분류로 넓은 카테고리를 국밥/고기구이/초밥 등 추천에 쓸 수 있는 세부 분류로 정규화
  • 비음식점 업종 필터링 + name·address 복합키 중복 제거로 최종 2,343개 · 핵심 컬럼 결측 0건의 서비스용 데이터셋 완성
  • Rule-based Weighted Scoring 추천 — 기본 40점에서 예산·맵기·간·식단·성향을 반영해 0~100점 산출, 평점 가산 / 재방문 거부·최근 추천 감점, 실시간 날씨 보정까지 결합
  • 상위 후보에 ±15% 랜덤 변동·카테고리 다양성 보정으로 추천 반복 방지, Haversine 거리 계산 기반 주변 식당 TOP 5 추천
프로젝트 자세히 보기
데이터가 먼저였습니다

추천 앱의 핵심은 화면이 아니라 "추천할 수 있는 데이터"라는 판단으로, 원천 데이터의 행·컬럼 구조와 결측 분포 확인부터 시작했습니다. 원천에는 음식점이 아닌 업종, 주소·좌표 결측, 서비스 목적과 맞지 않는 카테고리가 섞여 있었습니다.

의미 기반 결측 처리

좌표·주소는 평균 대체가 무의미한 위치 데이터이므로 Kakao Local API 재조회로 보강하고, 검색어에 지역명을 붙여 동명 식당 오매칭을 줄였습니다. 카테고리는 '기타' 임시 처리 후 음식점명·브랜드 키워드로 재분류했고, 비음식점 업종 제거와 name+address 복합키 중복 제거를 거쳐 최종 2,343개 · 핵심 컬럼 결측 0건 데이터셋을 완성했습니다.

추천 로직

기본 40점에서 예산·맵기·간·식단·성향으로 가감하는 Rule-based Weighted Scoring으로 0~100점을 산출합니다. 높은 평점 메뉴 가산 / 재방문 거부·최근 추천 메뉴 감점, 실시간 날씨 보정을 결합하고, 상위 후보에 ±15% 랜덤 변동과 카테고리 다양성 보정을 적용해 성격이 다른 점심 메뉴 3개를 추천합니다.

위치 기반 추천

GPS 좌표와 식당 좌표 간 Haversine 거리를 계산해(80m당 도보 1분 환산) 거리순 TOP 5 식당을 지도와 목록으로 제공합니다.

Movie Recommendation — 콘텐츠 기반 영화 추천

개인 프로젝트
2025.11 (2주) · TMDB 5000 데이터셋 기반 · Streamlit 웹앱

영화 한 편을 선택하면 줄거리·장르 기반으로 유사 영화 10편을 포스터와 함께 추천하는 웹앱.

모델링 포인트

  • 줄거리와 장르를 결합한 추천 문장을 TF-IDF 벡터화 → 코사인 유사도로 유사 영화 산출
  • 장르 반영이 약한 문제를 장르 텍스트 반복 가중 결합으로 개선한 2차 모델 구축, 기본 모델 자동 폴백 구조 적용
  • TMDB API 연동으로 포스터·한국어 제목 표시, API 키 부재 시에도 추천이 동작하는 예외 처리 설계
프로젝트 자세히 보기
추천 문장 설계

줄거리(overview)만 쓰면 장르 반영이 약해지는 문제를 발견하고, 장르 텍스트를 3회 반복 결합한 추천 문장으로 장르 가중치를 높인 2차 모델(cosine_sim2)을 만들었습니다. 로딩 실패 시 기본 모델로 자동 폴백합니다.

모델링 · 서빙

TfidfVectorizer로 벡터화하고 cosine_similarity로 영화 간 유사도 행렬을 계산해, 자기 자신과 중복을 제외한 상위 10편을 반환합니다. 학습 산출물은 pkl 바이너리로 직렬화해 앱 기동 시 재계산 없이 로드합니다.

예외 처리

TMDB API 키가 없거나 포스터 조회에 실패해도 추천은 동작하도록 기본 이미지·원제 표시로 대체하는 흐름을 설계했습니다.
